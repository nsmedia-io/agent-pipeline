# Changelog

Behaviour changes that reach an existing project at its next plugin update, newest release first. Each entry says what changes on its own and what to do, if anything. Records an older release wrote can be checked, and their mechanical part normalised, with `scripts/migrate-records.mjs`; see Unreleased.

Entries keep the numbers they carried in the README's old Upgrading list, so a cross-reference such as "item 29 below" still resolves. Measured figures in an entry describe the commit that entry shipped with and are not re-taken afterwards.

## Unreleased

### Upgrading from an older install, and the records it left behind

**Find out whether you are behind.** Hooks, gates and agent contracts load from the installed plugin cache (`~/.claude/plugins/cache/agent-pipeline/pipeline/<version>/`), not from your checkout, and one machine ran 0.24.0 hooks while 0.42.0 was published with nothing saying so. `scripts/version-check.mjs` now runs at SessionStart and in `/warmup`. It compares the running `plugin.json` version with the marketplace clone under `~/.claude/plugins/marketplaces/agent-pipeline/` and with every other version directory in the cache, makes no network call, and prints one line naming both versions and the update command (`/plugin marketplace update agent-pipeline`, then `/plugin update pipeline@agent-pipeline`, then restart the session) when the running copy is older. Silence means nothing newer is on this disk, not that you are current: the clone is only as fresh as its last marketplace update.

**Check your records after updating.** `scripts/migrate-records.mjs` reads every `.pipeline/<issue>/status.json` and review shard in a project and reports what the current schemas reject: a `current_phase` outside `<phase>-<slug>` (such as `phase3_complete_rev21`), missing required status fields, non-ISO timestamps, concerns missing `severity`, `likelihood`, `harm`, `merge_class` or `must_satisfy` (or carrying a value outside that field's enum), and vulnerabilities missing `remediation`. It is a dry run by default:

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/migrate-records.mjs" --root .           # report only
node "$CLAUDE_PLUGIN_ROOT/scripts/migrate-records.mjs" --root . --write   # apply the mechanical fixes
node "$CLAUDE_PLUGIN_ROOT/scripts/migrate-records.mjs" --root . --check   # exit 1 while anything needs attention
```

`--write` changes two things and nothing else. A run whose record carries a merge (`merged_at`, `merge_commit`, or an `events[]` verdict of `merged`) gets `current_phase: "5-archive"`; a rejected phase with no merge record is reported for you to set, because a run that stopped without merging is not archived by inference. A status record with no remaining problem gets `schema_version` stamped. Review shards are never written: a missing likelihood, harm or merge class is the reviewer's judgement, and the script does not invent one. Directories starting with `_`, such as `_archived/`, are skipped.

### In this release

Review convergence. Measured on one consumer before these changes: a single tooling issue ran 21 spec revisions and 8 Phase 4 panel rounds with six reviewers, and produced 79 acceptance criteria, a 676-assertion prover and 35 follow-up issues. Every finding was real; almost none could have cost a user anything. Items 43 to 50 are the changes that stop each of those.

43. **A review finding blocks only when merging it would cost something, and every concern now says what.** Phase 4 concerns REQUIRE four ratings: `severity`, `likelihood`, `harm` and the new `merge_class` (`wrong-pass`: a gate or test reports green on a real failure; `money`; `data-loss`; `security-exposure`; `none`). `harm` gains `money`, and `reversibility` becomes optional. A concern blocks only when its severity is blocker, critical or high, its `merge_class` is not `none`, and its likelihood is `normal-use`; a `product-money` run also blocks on `edge-case`, a `security-exposure` also blocks at `adversarial`, and a `tooling` run blocks only on `wrong-pass` or `security-exposure`. The cap of two blockers per reviewer is now enforced: the rest are demoted to notes, ranked by `merge_class` then `harm`, and the demoted ids are listed back to that role on the next delta round. Every blocker/critical/high concern must carry a stable `id` (the validator refuses one without); a legacy blocker with no id is named by position and flagged in `materiality.positional_ids`. The merge recomputes `materiality` from the concerns on every pass and never keeps an incoming record, so a hand-written or stale `blocks_merge:false` cannot stand. A `VETO` stands only from SecOps, on a valid `veto_ground`, with a blocking concern; otherwise it does not send the spec back to BA. A `REQUEST_REFACTOR` with no blocking concern is a note. The final-verdict rubric reads `materiality.blocks_merge` and the new `materiality.open_blocker_ids`. **What changes for you:** a finding that used to loop a run can now ship as a note, on purpose. A shard written before this change carries no `merge_class`, so each of its concerns is read as an UNRATED NOTE (flagged in `materiality.unrated_ids`), never as a blocker. **In-flight runs:** re-dispatch any panelist whose unrated blocker you still want to block, or add `merge_class` (and any missing `likelihood`/`harm`, plus an `id` on each blocker) to that shard's concerns yourself before the merge; the SubagentStop validator refuses a new panel shard whose concern is missing one of the four ratings.
44. **`status.json` gains the fields the budgets count, and a `cost_class` BA sets.** New keys: `cost_class` (`product-money | product | tooling`, set by BA in `spec.json` and copied over by the orchestrator), `fix_rounds`, `spec_revisions`, `owner_overrides[]` and `schema_version` (2 for this contract). **What to add to an existing `status.json` of a run you will resume:** `"schema_version": 2`, `"cost_class": "<product-money|product|tooling>"`, `"fix_rounds": <Phase 4 fix rounds already run>` and `"spec_revisions": <BA reworks after Phase 2 already run>`. Leaving them out is safe but lenient: the budget reads a missing `cost_class` as `product` and a missing counter as 0, and says so on stderr.
45. **Round budgets are counted in code (`scripts/round-budget.mjs`), not prose.** `enter fix-round` runs before every Phase 4 fix round (budget: `tooling` 1, `product` 2, `product-money` 2) and `enter spec-revision` before every loop back to BA after Phase 2 (budget 2). Past the budget it exits 2 and prints a plain-language decision for the owner: ship with deferrals, split, or stop. The owner's choice to keep going is recorded as an `owner_overrides` entry (`{"kind": "fix-round", "up_to": 3, "at": "<iso>", "reason": "..."}`), and only that lifts the refusal. `checkRoundBudget` is exported for a phase-entry gate to call. `spec-size` REFUSES a `tooling` spec with more than 12 acceptance criteria and no `size_justification`.
46. **The panel prompt stops asking reviewers to find a flaw.** The "do not hunt for reasons to approve; surface the single strongest flaw" stance is replaced by: report the most serious real defect your lens finds, with evidence; if nothing reaches a `merge_class`, APPROVE with at most three notes; an evidenced APPROVE is a complete review. The evidence rules (cite file:line, a grep needs a control that shows it can match) stay. A delta round no longer tells reviewers to assume the fix introduced a defect: each rules on its own open blocker ids, listed in its prompt (`render-panel.mjs --peer-review <peer-review.json>`), and a new finding blocks only if the fix commits introduced it and it has a `merge_class`.
47. **A delta round reseats fewer roles.** The seed is the roles holding open blocker ids (read from `peer-review.json`, not typed), and a role is added by surface only where the fix touched its merge-class surface: DBA on the data layer, SecOps on security paths (and the data layer, except at `tooling`), QA on test files, DevOps on infra (except at `tooling`). Design no longer re-sits on a frontend-only fix unless it holds an open blocker. SecOps seating on a FULL round is unchanged and mandatory.
48. **A `tooling` change gets a small panel and a lighter evidence bar.** At `cost_class: tooling`, whatever the tier, the panel is QA, SecOps and ONE surface specialist (DevOps, DBA or Design when the diff touches their surface, else Dev), for one fix round, with SecOps at `medium` effort (`dispatch-effort.mjs --cost-class tooling`). `evidence-controls.md` binds a tooling change only on a gate's own pass/fail logic or when the diff touches auth, secrets or the pipeline's own hooks. QA records `test_cost` (assertion count and pre-push seconds, before and after); growth past 100 assertions or 30 seconds at `tooling` becomes a consolidation note.
49. **Notes go onto one checklist per issue.** `deferral.mjs checklist --issue <n> --peer-review <file>` writes every Phase 4 note as one checklist entry through your configured `deferralTracker`, and opens a separate entry only for a note with a `merge_class` other than `none` or one the owner names with `--own`. If you scripted `deferral.mjs record` once per note, switch that step to `checklist`.
50. **Contradictions fixed.** Design's lens no longer says a `major` concern can justify `REQUEST_CHANGES` (a major never blocked). The peer-review schema's description of the trivial-tier panel now says QA plus SecOps, which is what the orchestrator seats. The `veto_ground` list is defined once, in the new `schemas/definitions.schema.json`, which `review.schema.json` and `peer-review.schema.json` both reference; the validator resolves that sibling-file reference. The merge takes `--status <status.json>` (or `--cost-class`) so it knows the run's cost class, and refuses to guess when that file cannot be read.
51. **A malformed `current_phase` is refused instead of quietly switching the phase-entry guard off.** `check-status-record.mjs`, which the checkpoint recipe already runs before every `status.json` commit, now also refuses a `current_phase` that does not match the pattern in `status.schema.json` (for example `Phase 3` or `3_impl`), and names the file. The Stop hook's phase-entry guard refuses to end a turn at such a phase while the run is in flight, where it used to treat it as an unknown phase and check nothing for the rest of the run. A well-shaped phase the guard has no row for is still let through, as before. The SubagentStop validator no longer stops recognising a run directory because its phase is mistyped. If a run of yours is refused, fix the phase in `status.json` and commit it.
52. **A check that could not run now says so.** Every hook still lets your session continue when its own tooling is missing or broken, but it no longer does that in silence. A crashed PreToolUse gate, a Stop hook without node or without the guard script, a voice lint that cannot read its schema or the transcript, a SubagentStop hook without its validator, and a warmup that cannot start each print one line, "pipeline check X did not run: reason", which Claude Code shows to you, and append it to `agent-pipeline-disarm.log` in the repository's git directory. The next session warmup lists those lines once and then sets the log aside. `CLAUDE_HOOK_STOP_SKIP=1` now leaves the same record. A project that has never run the pipeline (no `.pipeline` directory) stays quiet.
53. **Acceptance-criteria coverage matches a criterion's own label only.** The pre-Phase-4 gate used to count `AC3` as covered when any entry merely mentioned `AC3`, for instance in its notes. A labelled criterion is now covered only by an entry whose own leading label is that label (`requirement_text` of a check, `criterion` of an `acceptance_criteria_met` entry) or whose new optional `ac_id` field names it. Word overlap is still used for criteria without a leading label, and the gate now prints how many criteria each method decided. This can halt a report that passed before: start the covering entry's text with the label, or set `ac_id`.
54. **The gate no longer passes a migration check over zero files.** When `migrationGlobs` in `pipeline.config.json` matched none of the files the implementation report changed, but the mis-tier tripwire recognised some of them as migrations, the down-section check used to pass with nothing checked. The gate now halts, names those files and points at `migrationGlobs` and `extraMigrationGlobs`. A config that still finds at least one migration keeps its narrowing. The #152 case (a TypeScript helper under `migrations/__tests__/`) was already excluded by #156 and is now pinned by a test.
55. **Subagents may not run destructive git.** The PreToolUse hook refuses `git stash` (except `git stash list` and `git stash show`), `git reset --hard`, `git checkout -- <paths>`, `git checkout .`, `git restore` of working-tree paths and `git clean` when the call comes from a subagent, at any phase, because a subagent's tree is shared and what these discard may not be its own. The refusal says why and what to do instead. Your own main-session commands are unaffected. QA's mutation battery now restores a file with `git show HEAD:<path> > <path>` instead of `git checkout --`.
56. **A reviewer's shard written into the wrong checkout is caught at its stop.** When an agent dispatched into a worktree writes `review.<role>.json` or `peer-review.<role>.json` into the main project's `.pipeline/<issue>/` during its run, and the worktree has no copy, the SubagentStop validator refuses the stop and names both paths. The merge's `MISSING SHARD` message also names any same-named file it finds under the project's `.pipeline/`.
57. **The SubagentStop validator works for plugin-installed agents, and `map.json` is validated (fixes #66).** The validator already stripped the namespace from agent types such as `pipeline:qa`; it is now tested end to end through the hook with namespaced names, including a control showing the old lookup would go silent. `map.json` is now checked against `map.schema.json` when BA stops.
58. **Agent frontmatter is linted at warmup.** `config-doctor.mjs` parses the frontmatter of the plugin's agents and of `.claude/agents/*.md` with a small dependency-free YAML subset parser, and reports parse errors (an unquoted `: ` in a value, an invalid escape, text after a closing quote, a duplicate key, a tab indent, an unclosed block), a missing `name` or `description`, and a `model` or `effort` outside the known values. Origin: a project agent whose description carried an unquoted `: ` failed to load with no message.
59. **A consumer-owned config namespace.** The config doctor's "read by nothing" warning now names the remedy: put project-owned settings under the `x` object, or in a key starting with `_`. The plugin never reads inside either, and the doctor never reports them. `architecturalTriggers` is documented as advisory: no script reads it, and `keywords` is a hint to the BA agent's judgment rather than a mechanical trigger.
60. **The suite runs under Git Bash on Windows.** Root cause of the mass failure: about a hundred test sites load a module with `import(<path>)`, and node's ESM loader refuses every spelling bash hands it on Windows (`C:/x` after Git Bash's argv and environment rewrite reads as a URL scheme; `/c/x` or `/tmp/x` inside JS source is not a Windows file URL). `tests/harness.sh` now preloads `tests/fixtures/windows-esm-paths.mjs` through `NODE_OPTIONS` on MINGW, MSYS and CYGWIN only, which maps those specifiers to file URLs and leaves `require()` alone; the harness's ledger directory no longer uses `mkdir -m 700`, which on Windows creates the directory and then fails, disabling the uncounted-assertion guard in every suite. `scripts/lib.mjs` gains `nativePath` for scripts that receive an MSYS path. The shipped scripts never `import()` a path, so consumer hooks did not have this defect.
    Measured on one Windows 11 host (Git Bash, MINGW64 3.6.3, node 24.13.1), whole `bash tests/run.sh`: at 36522fc 826 failing rows across 54 suites (36 suites red); after this change 191 failing rows across 58 suites (16 red), 232 minutes wall clock. What is still red there, by cause: scripts print native `C:\...` paths and `\` separators where assertions expect `/tmp/...` and `/`; fixtures pass POSIX paths inside stdin JSON or file content, which Git Bash does not rewrite (voice-lint, archive redaction, render-panel); bash-script CLI stubs such as a fake `gh` that node cannot spawn; the checkout's CRLF line endings under `core.autocrlf=true` (label pins, byte-identity and single-line rewrite checks); POSIX-only semantics (symlinks, chmod, an unwritable directory, hiding node by trimming PATH, a 72 KB argv); and the nested fresh-checkout run, which inherits all of these. On Linux the suite is unchanged: the preload is never loaded there.
    The PreToolUse hook's declared 30 s timeout on that host: the largest real fixture the timeout-bound suite times, `knowledge/issue-archive/106.json` staged as a heredoc (465,635 command bytes), decided in 4,598 ms min-of-3 before this change and 4,300 ms after it (8,618 and 8,059 ms with the suite's 1.42 x 1.32 load factors), so it does not trip. The suite's constructed dense cell (about 5 MB of concatenated `tests/test-materiality.sh`) takes 60 to 66 s and is killed at 30 s, which is that cell's purpose: it demonstrates the fail-open kill, and it was sized to exceed the bound.


## 0.42.0 (2026-09-14)

39. **The Phase 4 merge REFUSES a provisional shard exactly as it refuses a missing one (0.42.0, #155).** `merge-peer-review.mjs` exits 2 naming the role when a shard's top-level prose declares the review unfinished (`provisional`, `in progress`, `not yet complete`, `placeholder`, `will update before final`, `review pending`) or when it carries no concerns and no evidence-bearing text at all (the bare `{"verdict":"APPROVE"}` placeholder). Nothing is written on a refusal, so a standing delta verdict is never clobbered by a placeholder. Origin: two panelists ran out of turns and left placeholder shards; the merge folded both in as real APPROVE_WITH_NOTES verdicts and the orchestrator caught it only by file size. A terse real shard (`notes: "clean"`), an APPROVE_WITH_NOTES carrying one concern, or a VETO carrying its `veto_ground` all still merge; the threshold is "nothing", not a word count.
40. **A TEST FILE under a migrations directory is never a migration (0.42.0, #156).** `isMigrationPath` now excludes `.test.*` and `.spec.*` basenames and any `__tests__/`, `tests/` or `test/` path segment before matching the glob set, code-resident like the existing `.md` exclusion and therefore not a config off-switch. Both the mis-tier tripwire and the pre-Phase-4 gate's down-section discovery read this predicate, so both stop firing on a project that keeps TypeScript tests ABOUT its migrations beside them (69 such files, zero SQL, on the origin project). Extensions are deliberately NOT allowlisted: the preset rows for Drizzle `schema.ts`, Prisma and Rails would be disarmed by any extension list short enough to be correct. If your project keeps a REAL migration under a `tests/` directory, add its path to `extraMigrationGlobs`; the exclusion runs before the glob match, so name the file rather than the directory.
41. **The Phase 4 panel Workflow script is RENDERED, not hand-written (0.42.0, #157).** `scripts/render-panel.mjs --status <status.json> --worktree <path> [--delta "<roles>" --first-round-head <sha>] --check --out <file>` prints a parse-valid Workflow script whose reviewed sha is `git rev-parse HEAD` of the worktree (never typed), whose preamble is sliced from `commands/pipeline.md` between `<!-- BEGIN PHASE4-PREAMBLE -->` and `<!-- END PHASE4-PREAMBLE -->` (one copy of the prose), whose lens per role comes from the new `scripts/panel-lenses.json` (one lens table; the command file no longer carries a second copy), and whose per-role `model` and `effort` come from the two dispatch resolvers. Every string passes through `JSON.stringify`, so no quoting class can break the script. `--check` parses the result under the runtime's async wrapper. If you had wrapped the panel dispatch in your own harness, the shard files and the merge are unchanged; only the way the script text is produced moved.
42. **QA's Phase 3a contract must be proven SATISFIABLE, and the SubagentStop validator refuses a QA stop without the record (0.42.0, #158).** At the architectural tier QA writes `satisfiability_proof` into `tasks.json` before returning: `reference_impl_run` plus `criteria_proven[]` (the criteria a throwaway implementation took green) or `criteria_unproven[]` (each with its reason), and `configs_run[]` naming every test config or pool the committed files land in. `groundSatisfiability` blocks the QA stop when the block is absent or names no criterion in either list; it is off below the architectural tier and off once `impl-report.json` exists (the Phase 4 QA stop). The orchestrator halts before dispatching Dev on the same condition. Test-discipline rule 12 already asked for the reference implementation; this is its enforcement. Companion: `dev.md` now permits a DISCLOSED repair to a QA test that is unsatisfiable by any implementation, recorded in `impl-report.json` `test_side_repairs[]` (`weakened` must be `false`), with QA's Phase 4 ruling on each entry binding. Origin: 129 cases handed over red-but-unproven, three unsatisfiable, Dev's turn cap spent repairing them.

## 0.41.1 (2026-09-07)

35. **BA's blast-radius map and the Phase 4 blast-radius lens now enumerate the READERS OF A FIELD, not only the callers of its producer (0.41.1).** When a change writes a value into a field of a shared data object (an array on a window-data record, a property on a message, a slot on a rendered payload), the value reaches every consumer of that object, and a consumer that only reads the field never shows up in a grep for the function that filled it. `agents/ba.md` duty 1, the `readers.typescript` description in `schemas/map.schema.json`, and the Phase 4 blast-radius rule in `commands/pipeline.md` all carry the rule now. Origin: a composed digest note was written into one array that three functions read; the map, both design sketches and the judge listed the composer's callers, and a settings pointer reached the summarization prompt and the fallback narrative until the Phase 4 panel found it. Prose and schema-description only, nothing mechanical enforces it yet.
36. **A Phase 2 re-run after `REQUEST_CHANGES` is a DELTA, mirroring the Phase 4 delta re-review (0.41.1).** The orchestrator re-dispatches the reviewer(s) that objected plus any reviewer whose lens the BA rework touched (a new data-layer requirement re-seats DBA, a deploy or binding requirement re-seats DevOps, a caregiver-facing string re-seats Design, and any logging, retention, auth or copy requirement re-seats SecOps); the standing approvals of untouched reviewers carry into `review.json` unchanged, the prior round is kept as `review.round1.json`, and `status.json` records `phase2_round` plus a `2-review` event naming the subset. "Re-run Phase 2" read literally was four reviewer spin-ups for a rework one of them asked for, and that is what the round budget was counting.
37. **A BLOCKING Phase 4 concern carries its deciding test as `suggested_patch` whenever that test is local (0.41.1).** One test file, about forty lines or fewer: the fix round then starts from a red test that encodes `must_satisfy` rather than from a property Dev re-derives, and the delta re-review has one fewer thing to argue about. Origin: on one issue the fix rounds that converged in a single pass were exactly the ones where the objector had supplied the failing test. Panel-prompt prose; the merge does not require the field.
38. **Every Phase 4 shard is PARSE-CHECKED by its author before the agent returns (0.41.1).** The panel prompt now ends with a one-line `JSON.parse` check of the shard path and a reminder that `likelihood`, `reversibility` and `harm` are enum tokens, never sentences. Origin: one shard carried a stray closing bracket and another carried prose ratings; the merge refused both, correctly, and the orchestrator hand-repaired them, which is a repair no shard should need. If you have wrapped the panel dispatch in your own harness, the check is a prompt instruction and costs nothing to keep.

## 0.41.0 and earlier (up to 2026-09-05)

Items 33 and 34 name the release they shipped in; items 1 to 32 predate per-item version tags.

1. **The migration/data-layer/infra glob defaults are now a fifteen-row framework-preset union** (Rails, Django, Alembic, Prisma in both layouts, Drizzle, Supabase in both workflows, Flyway, Liquibase, EF Core, Laravel, plus the generic declarative dumps), **and the mis-tier tripwire can no longer be narrowed by config.** `migrationGlobs` unions with those presets for the tripwire, so a vendored or fixture path under a `migrations/` directory that never halted a run before now WILL, once per path, loudly and recoverably. Widen with `extraMigrationGlobs`; narrowing the tripwire is deliberately impossible, because a halting control bound to a narrowing knob can be disarmed by a four-character edit that reads as tuning. A Markdown docs path is excluded from the narrow set in code, so a `.md`/`.mdx` file under `migrations/` does not halt. Any other extension there does, including `.txt` and images: the exclusion is two extensions, not a notion of "documentation", and it stays that way deliberately. Chasing further spellings would put the guard on the wrong side of the transformation, and the halt it produces is loud, once-per-path, and recoverable.
2. **Editing `pipeline.config.json` now forces the architectural tier.** That file decides whether the tripwire fires, who sits on the Phase 4 panel, and which model renders a binding verdict, so a diff touching it gets the pre-code SecOps review.
3. **If you copied the example config, DELETE its `migrationGlobs` line.** The example used to ship `"migrationGlobs": ["**/migrations/**"]`, and that key REPLACES the preset union for the pre-Phase-4 gate's discovery. Left in place, the gate discovers nothing for a Rails, Alembic, EF Core, Drizzle, declarative-Supabase or Flyway layout while the tripwire still fires: the pipeline re-tiers the change as a migration and then runs a reversibility check over zero files. Set `migrationGlobs` only when you specifically want to narrow gate discovery.

4. **The pre-Phase-4 gate now REFUSES a down region that is executable SQL, or that carries an unterminated block comment**, where it previously accepted any region carrying the marker string. It classifies everything after the marker LINE in one left-to-right scan; block comments do not nest there, and a `/*!` or `/*M!` opener is refused outright because MySQL/MariaDB execute those bodies. The refusal is bounded to migrations the current change adds or touches, never a project's existing backlog. TWO COSTS, named separately because one does not cover the other. First, MySQL's `# line comment` syntax is not recognised as a comment (it is not one in PostgreSQL, SQLite, Oracle or T-SQL), so a project whose down regions use `#` has EVERY such line refused: the remedy is a per-line substitution to `--` across the migrations this pipeline touches, NOT a one-line edit. Second, and separately, the gate now classifies from the END of the marker line, which makes a non-comment MARKER such as `# DOWN` safe; that does nothing for a down BODY written in `#` line comments, which is the first cost above.

5. **`phase_elapsed_ms` is now keyed by the phase each event CLOSED, not the one it was previously read as opening.** `events[]` entries are exit markers (each carries the verdict of the phase it closes), so every figure was shifted one slot and the final phase of every run received no key at all. Figures in `status.json` records written by 0.21.0 or earlier were computed under the old convention and are NOT automatically recomputed: treat them as historical and stale rather than migrating them. Read the new `attribution` field to tell which convention a block was computed under — its absence means the old one.

6. **A turn can now be REFUSED at its end.** `hooks/stop.sh` runs a phase-entry guard: if `status.json`'s `current_phase` names a phase whose prerequisite artifact is absent, and the run is still in flight, the turn is blocked with a message naming the phase, the missing prerequisite and the issue directory. This is the one place the plugin is deliberately fail-CLOSED on its decision, and `CLAUDE_HOOK_STOP_SKIP=1` does NOT bypass it, because a halting control with an opt-out knob is not a halting control. THREE THINGS BOUND IT so it cannot wedge you. It only evaluates a run that is in flight (`updated_at` within `IN_FLIGHT_MS`, and no `final_verdict`), so an abandoned or concluded run never blocks a project. That predicate is not restated here or anywhere else: `scripts/run-candidates.mjs` owns it, and `scripts/pipeline-status.mjs`'s "possibly stuck" filter reads the same function, so the reporter and the guard cannot disagree about the window (#74). `final_verdict` means the run concluded and not merely that it concluded once, because the checkpoint that enters `4-review` for a delta round clears it (#110). Its refusal always names a clearance route: produce the artifact, record a `SKIPPED` deviation with a non-empty note in `events[]`, or conclude the run. And it stays fail-OPEN on TOOLING: if node or the guard script is missing the turn proceeds, and the session-start warmup says so once per session, because a missing install is your environment rather than the orchestrator exercising discretion. What it does NOT do: it fires at the turn BOUNDARY, not before a dispatch, so it cannot make skipping a phase impossible. It makes an unrecorded skip become either a blocked turn or a recorded, reasoned one.

7. **Review can now STOP ITSELF instead of looping.** After the SECOND Phase 2 round returns any `REQUEST_CHANGES`, the orchestrator no longer loops back by default: it halts and puts **split / defer / proceed** to you with a recommendation. A third round happens because you chose it. Paired with this, BA must justify or propose a split once a spec crosses **10 requirements or 12 acceptance criteria**. Neither is a hard limit and neither refuses correct work; both exist because every loop-back is individually justified, so a spec can round-trip indefinitely while each round looks like the gate working. Measured on one run before this change: three Phase 2 rounds, four spec revisions, an 86KB spec that grew to 95KB while its substance halved, and zero lines of code, with every blocker in every round real. If your runs never reach a second `REQUEST_CHANGES` round, you will never see this.

8. **`events[].verdict` and `flags[].verdict` are now capped at 32 characters, and `commands/pipeline.md` restates that cap as a writer rule.** Write the verdict TOKEN and nothing else; reasoning belongs in `summary` or `note`. Be clear about what this is: `status.json` is validated against `status.schema.json` by NOTHING (the file is in no `AGENT_RULES` entry, and that walker does not implement `maxLength` at all), so the cap refuses nothing at write time. It is enforced by a new corpus-conformance suite that walks every committed `.pipeline/*/status.json` on every pull request and reddens if any stored verdict exceeds the cap read FROM the schema. So this detects rather than prevents, and it detects before the record reaches your integration branch. No committed record is invalidated: the longest verdict that exists, declared or observed, is `APPROVE_WITH_NOTES` at 18 characters. The sibling free-text fields (`events[].note`, `veto_reason`, `error`) are deliberately NOT capped, because a length bound would refuse their correct work; the exposure question for those is tracked separately.

9. **The phase-entry guard now ABSTAINS on a tier it cannot determine, instead of applying the strictest row.** Previously an absent, null or malformed `risk_tier` normalised to `architectural`, which switched on the `1-ba` row and demanded a `map.json` that the standard and trivial tiers never produce separately. Because `risk_tier` is BA's output and `1-ba` is checkpointed BEFORE BA is dispatched, the tier is necessarily absent on a run's first visit there, so **the guard refused turn one of most runs**, and the honest clearance route its own message named did not exist at two of the three tiers. It now treats a tier-restricted row as not applying while the tier is undetermined. **What this costs, stated plainly: the `1-ba` map requirement is retired on the mandated path at EVERY tier, not narrowed.** Measured across 75 phase-by-tier combinations, exactly two change, both at `1-ba`. Re-siting that requirement where the tier IS resolved is tracked separately.
10. **The pre-Phase-4 gate's up-section and acceptance-criteria coverage checks are both stricter.** The up-section test was a line-prefix match, so a fully block-commented region counted as present; the coverage matcher passed on token overlap between a criterion and a requirement check. Both said yes too easily. **A change that passed this gate before may now fail it**, which is the intended direction: these are the checks standing between a half-written artifact and the review panel.
11. **Absolute filesystem paths are redacted when a run is archived into the knowledge store.** `archiveIssue` now rewrites by value SHAPE across the whole document, keys included: paths under the repo root become repo-relative, everything else becomes `<redacted-absolute-path>`. This exists because `tasks.json` and `impl-report.json` both carry `worktree_path` absolutely and the archive is committed, so a developer's home directory was reaching a public tree. The predicate replaces the path SPAN and not the whole value, so a descriptive string like `/tmp/x (detached at abc123)` archives as `<redacted-absolute-path> (detached at abc123)`: the path goes, the evidence around it stays (#59).
12. **An mtime tie when resolving which run a session owns now yields NO subject, rather than whichever directory `readdir` returned first.** A fresh `git clone` writes every tracked `status.json` inside one coarse clock tick on Linux, so all of them share an mtime and the old behaviour picked a run by filesystem order. The guard now abstains, which lands on its existing fail-open tooling branch. Combined with item 9, the guard has three distinct ways to produce no decision; they are enumerated in its own header comment so the next person adding a fourth can see the first three.
13. **The orchestrator's `surface_probe` now passes its two arguments in brace form (`"${1}" "${2}"`), in both definitions.** This is the one change in this release whose fix is invisible in a plain-bash reading: the two forms are identical to a shell. `commands/pipeline.md` is a slash-command TEMPLATE, and the loader substitutes bare `$N` tokens in the text before a shell runs it, so a rendered copy could lose the arguments and exit 1 (INDETERMINATE) on every panel and frontend surface probe, which the caller reads as a broken probe rather than a broken template. **Until your installation refreshes, your sessions keep running the old form**, because `/pipeline` and the agent contracts are loaded from the installed plugin cache and not from your checkout; nothing in the repository re-syncs that cache on merge, and no check runs in that runtime, so nobody is notified when the window closes. The same applies to every enforcement claim the agent contracts and the two review schemas make in this release: they describe the source tree, and reach your sessions at your next plugin update.
14. **A Phase 2 `review.json` written before this release can BLOCK a `dba`, `devops` or `secops` stop for thirty minutes after you upgrade.** This release adds `must_satisfy` to the required list on review `concerns[]` items and `remediation` to SecOps `vulnerabilities[]` items. The check is keyed to the STOP, so a merged Phase 2 record is re-read at every later stop of the same type while the file's mtime is inside the 30-minute recency window - which means a Phase 4 panellist can be blocked on a Phase 2 block it did not write. **Measured on this repository's own in-flight run:** `dba` 4 failures, `devops` 2, `secops` 5, all `missing required field "must_satisfy"` on `review.json`, with the other six roles silent in the same run. **Who this reaches:** only a run still in flight at the moment you upgrade, and only for thirty minutes per touch of that file; nothing revalidates `knowledge/issue-archive`, and an artifact older than the window is skipped. **What to do:** let the file age out of the window, or re-run the Phase 2 reviewer that owns the block. Do NOT backfill the field into another role's finished record - `''` satisfies it and writes a property nobody stated into a record that is about to be archived and committed. **Scale of the retroactive reach, so you can judge it before upgrading:** over one measured corpus of already-written artifacts, 17 of 229 vulnerability rows carry no remediation (7%), and on the concerns side 488 of the 488 rows the required list governs carry no `must_satisfy` at all (100%). If you would rather not meet this mid-run, upgrade between runs.

It is now a hardcoded floor inside `ba.md` itself, so it holds with zero config content, and your own `architecturalTriggers.paths`/`.domains`/`.keywords` union onto the built-in list rather than define it (a config value can only add a trigger, never remove one). 16. **The Phase 0.5 blast-radius map requirement is enforced again, this time independent of tier, closing a gap the previous release opened.** Item 9 above made a tier-restricted phase-entry row abstain rather than refuse whenever the tier is not yet known. The `map.json` requirement lived on exactly such a row (`1-ba`, gated on `tiers: ["architectural"]`), and `1-ba` is always checkpointed BEFORE BA determines the tier, so that row could never actually fire on a run's first visit: an architectural-tier run that skipped Phase 0.5 and never produced a `map.json` passed the phase-entry guard at `2-review` with nothing to say about it. The `1-ba` row is untouched and still matters on a rework re-entry, once a tier is already recorded, but the real requirement now also lives on `2-review`, as a second check beside that row's existing approved-spec requirement. It needs no tier restriction of its own: `2-review` is a phase name only an architectural-tier run ever reaches, so the phase name itself is better tier evidence than the optional, sometimes-absent `risk_tier` field (#61).
17. **The no-secrets rule for `status.json` free text now covers all five fields it is committed and archived with, not just `ask_text`.** `events[].note`, `flags[].summary`, `veto_reason` and `error` are written by the orchestrator, committed to git, and copied verbatim into `knowledge/issue-archive/`, exactly like `ask_text` always was, and none of the four were named by the old rule. `error` is the sharpest: its natural content is copied machine output (a failed `gh`/`curl` call echoing a URL with a token, a database error carrying a connection string), which is exactly the shape a secret leaks in. This is a content rule, not a length one: beyond a pre-existing, unrelated 140-character digest bound already on `flags[].summary`, nothing here caps length, because a cap would refuse a field's correct work (a long note recording a real reproduction, say) without addressing the actual risk. A test suite now scans both the committed records and the archived copies for credential-shaped strings; if it fires on something already committed, the fix is to amend that commit, not to fix forward, since the exposure already happened in history either way (#52).
18. **A finished run's artifacts can no longer be silently archived stale.** The Phase 3-to-4 sync step used one blanket no-clobber copy for every artifact, which was only correct for the three files seeded before Dev starts (`spec.json`, `review.json`, `status.json`); it also froze the four files Dev and the panel produce IN the worktree (`map.json`, `tasks.json`, `impl-report.json`, `peer-review.json`) at whichever state was copied first, silently discarding any later fix, including one made during an APPROVE_WITH_NOTES nit round. The copy is now split by which side owns each file: the three seeded files still refuse to be overwritten, the four worktree-produced files now overwrite every time, and anything matching neither rule is copied on the safe no-clobber side and printed as unclassified so a new artifact type gets noticed instead of mishandled. Running the sync again right before archival is still only a written convention, not something enforced on itself, so the real backstop sits at archival: `archiveIssue` now compares each worktree-produced file against the worktree's own live copy and refuses to write the archive at all if they disagree, naming exactly which files diverged. It steps aside, neither checking nor refusing, once the worktree is already gone (routine post-merge cleanup makes this the common case) or when neither `tasks.json` nor `impl-report.json` recorded which worktree the run used. The one escape hatch is `PIPELINE_ARCHIVE_ALLOW_STALE=1`, which archives the stale copy anyway and says so on stderr (#58).


19. **Phase 4 panelists are now told, in their own contracts, that the shared dispatch worktree is READ-ONLY to them, and what an isolated tree has to be before it counts.** Isolation is owed by any panelist about to write a tracked file, not by the panel as a whole, so a reviewer that only reads is unaffected and stays where it is dispatched. A tree qualifies only when BOTH hold: `git -C <isolated> rev-parse --absolute-git-dir` EXITS 0 and DIFFERS from the dispatch worktree's own, AND `git -C <isolated> ls-files` exits 0 with a non-zero count. Not `--git-dir`, which prints a relative `.git` in a main checkout and so falsely refuses a real `git clone --no-hardlinks` while falsely admitting a tracked subdirectory of the dispatch tree; not `--git-common-dir`, which two linked worktrees share and which would therefore refuse `git worktree add --detach`, the mechanism the rule recommends. A `cp`/`tar`/`rsync` copy is not admitted, and what the check SAYS about one depends on your dispatch topology: where the dispatch tree is a linked worktree its `.git` is a FILE and a copy preserving it resolves to the SAME gitdir, so the check refuses it; where the dispatch tree is a main checkout that same copy is an independent repository and the check admits it. **A clone alone is not a pin** - it lands on the source's HEAD as it stands at clone time, and that tip moves inside a round, so pair it with `git -C <dest> checkout --detach <REVIEWED_SHA>`. **Location is stated as an outcome over the whole ancestor chain, not a blessed directory**, and as a disjunction: traversal needs other-execute on EVERY component, so one denying component denies the chain. Measure with the `ls -ld` walk the contracts carry rather than `stat`, whose format flags mean different things on BSD and GNU, or make the property true by construction with `install -d -m 700 <parent>`. **Two costs, named separately.** First, what you will SEE: a panelist that used to write in place now registers its own worktree, `git worktree list` grows, and nothing sweeps it - `git worktree prune` reclaims a registration only once its directory is already gone, so removal is the panelist's job and an agent cut off mid-run leaves one behind. Record the registry NAME rather than the path if you need to identify one later. Second, and this is the honest part: **nothing mechanically enforces any of it.** The rule is prose in nine agent contracts and in the `/pipeline` Phase 4 preamble; no hook, schema or test refuses a tracked write in the dispatch tree, and the commit-hygiene clause (`git status --porcelain` first, explicit paths only, never `git commit -a`/`add -A`/`add .`) is the one rule sited at the actual ship event and stops nothing either. Treat it as a stated standard a reviewer can be held to, not a control. Like item 13, it reaches your sessions at your next plugin update, because the contracts load from the installed plugin cache and not from your checkout (#19).
20. **The Stop-hook's voice check no longer re-fires for a decision it already forced you to explain, and can no longer be silenced by resending the exact message it just blocked.** The check decided whether a human turn had happened since it last fired from a single stale input, a `status.json` phase with no notion of who wrote it or when, so it re-imposed the full report shape on ordinary progress updates long after you had already been given the full context. The more serious half: its own refusal record satisfied its own definition of a human turn, so the control disarmed itself the instant it first fired, and resending the identical blocked message then passed. The boundary is now derived from the transcript itself and identified POSITIVELY (a record-level `origin.kind === "human"`, plus five guarded clauses on `type`/`isSidechain`/`isMeta`/`message.role`/`timestamp`) rather than by excluding known machine spellings, which is what had let the refusal record, background task-completion notices, and same-machine cross-session messages all pass as a person. Nine residuals are declared where the fix stops rather than chases a diminishing return, each with its own fail-direction and expiry written into the module header. The sharpest is a narrow, permission-error-only silent gap on the fallback status-resolution path (`EACCES`/`EPERM`/`EIO` on a foreign lane's `status.json`, not the common and correctly-silent case of a file archived out from under the scan mid-turn): left declared rather than forced closed, because the only mechanical fix moves the same silence to a different line instead of removing it. `resolveStatus` now returns `{status, dir, mtimeMs}` instead of a bare status object, and `isHumanTurnRecord` is newly exported; neither has an external importer today. Like items 13 and 19, this reaches your sessions at your next plugin update: `voice-lint.mjs` is a script your installed cache serves, not something re-read from your checkout on every Stop (#56).

21. **`spec.falsifiability_pass` is machine-checked now, and `/pipeline` no longer claims more than it checks.** The orchestrator has said for this block's whole life that "the table is machine-checked against the criterion list so the two cannot drift". Nothing checked it: `falsifiability_pass` appeared in ZERO scripts, and it sits outside `spec.schema.json`'s top-level `required`, so a spec could omit the block entirely and still validate. `groundFalsifiability` in `scripts/validate-pipeline-artifact.mjs` now runs on every `spec.json` the SubagentStop validator sees. **What it enforces is COVERAGE and only coverage:** every `AC<n>`-labelled acceptance criterion carries at least one row in `one_mutation_per_criterion` or `unmutable`, and at the architectural tier the block is present at all. Below that tier it fails open. **Three things are deliberately NOT refused**, decided by running the rule against the nine archived specs rather than from first principles, because a stricter gate would have refused five of the nine for doing good work: extra rows naming a residual or a premise rather than an AC (four archived specs use them on purpose), a criterion appearing in BOTH lists (#19's AC4 is partially unmutable, with the reason written down), and unlabeled criteria, which make the check ABSTAIN and say so rather than report a clean it did not measure. **Label your criteria `AC1. ...` or this gate enforces nothing** — it tells you when that happens. The failure is advisory in the SubagentStop sense the rest of that validator uses: a `{decision:"block"}` object on stdout, exit 0, asking the agent to fix the artifact before finishing. It reports nothing on all nine archived specs, so it costs existing work zero; it exists for the state the archive cannot show, every archived spec being a FINAL one — a spec REVISION that adds a criterion and no row for it.

23. **The pre-Phase-4 gate no longer crashes on a multi-repo implementation report.** A change spanning several repositories keys `commits` BY REPOSITORY. 27. **A blanket stage from a subagent is now REFUSED at the tool call, not merely forbidden in prose.** A new `PreToolUse` hook denies `git add -A`, `git add .`, `git add -u`, `git commit -a` and their equivalents when the call comes from a SUBAGENT and a run is in flight at a Phase 4 phase. The Phase 4 tracked-write isolation rule has always said this; the file also carried a closing concession that no mechanism actually enforced it, and that concession is now retired in all ten replicated copies. (The retired sentence is deliberately NOT quoted here: `test-pretooluse-doc-retirement.sh` bans it repo-wide, and a scanner cannot tell a quotation from a claim.) **The forbidden set is a CLASS over flag semantics, not a table of spellings**: the command is tokenised quote-aware, split at top-level operators, and every git invocation in it is judged, so `git commit -aqm 'm'` and `git add -Av` are caught although they match no enumerated row, while a commit message that merely QUOTES `git add -A` is not. **Scoped by ORIGIN, not by role**: the term is the payload's `agent_id`, which is set only inside a subagent, so the orchestrator's own status-only checkpoint commits are exempt by design and there is no role allowlist — which makes the refusal deliberately WIDER than the Phase 4 panel, since any subagent staging blanket during a Phase 4 run is denied whether or not it is a panelist. **FIVE COSTS, each measured rather than asserted, because a gate that surprises you is a gate you switch off.** (1) It OVER-DENIES a blanket flag standing beside any operand carrying a substitution, including one that RESOLVES to a real path: `git add -A packages/$PKG` is refused although a real shell would stage a correctly narrowed set, because `$PKG` holding a path and `$PKG` holding nothing are the same text to a scanner that never sees argv, and refusing the first is the price of denying the second. The refusal is loud and the rewrite is short — name the path literally, or stage and commit explicit paths. (2) It ABSTAINS entirely, enforcing nothing, when two or more runs are in flight in one `.pipeline` root and no explicit active-issue marker names one of them; that is deliberate (guessing wrong would refuse correct work) and the missing marker producer is tracked as #111. (3) It reads the COMMAND WORD and VERB literally, so `$GIT add -A`, `git $VERB -A`, `eval` and `sh -c "$CMD"` defeat it — a deliberate scope boundary, since those are adversarial rather than accidental, tracked as #118. (4) Its scan cost is LINEAR in command length and blind to structural density, but the constant is a shell interpreter's, so a large enough command still outruns the declared timeout and a killed hook FAILS OPEN, allowing the exact staging the gate exists to refuse. **The declaration is 30 SECONDS as of #132, raised from 5**, and both ends of the crossing were re-measured against it on darwin 25.5.0 / bash 3.2.57(1) in sh mode / node v24.19.0 rather than extrapolated. 32. **A heredoc body in a subagent's Bash call is now OPAQUE to the `PreToolUse` blanket-staging scanner, closing a live bypass of the `git add -A`/`git commit -a` refusal (#140).** The redirection arm at `pre-tool-use.sh` marked a heredoc delimiter as a redirect target but never treated the BODY as an opaque region the way the file already treats single-quote, double-quote and comment regions, so quote-tracking state leaked straight through it: an ordinary contraction ("it's") anywhere inside a heredoc body was enough to swallow the real terminator line and everything after it, including a trailing blanket stage. Closing either safely was judged to need real tokenization of the substitution interior, the same class of work the coarse rule above exists to avoid. **This fix does NOT touch a separate, more severe, pre-existing bypass found while reviewing it: bare backtick command substitution defeats this same blanket-staging scanner EVERYWHERE, not only in a heredoc, because backtick is not a member of the scanner's structural-character set at all** -- no heredoc, no quote games, just `` `git add -A` `` typed plainly, live on unmodified `main` today.
